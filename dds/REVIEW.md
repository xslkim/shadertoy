# DDS 两集视频脚本评审意见（从视频质量角度）

> 评审对象：`ep1/script.md`（B01–B24）、`ep2/script.md`（B25–B46）、两个 `meta.md`、`B00.wav`
> 评审依据：`D:\shadertoy\AUTHORING.md` 规范 + 成片观感角度
> 日期：2026-07-20

## 总体评价

脚本本身的写作质量很高：结构清晰（原理→横评→商业化→量产）、旁白节奏好、单行长度全部合规（实测最长未超 40 字）、关键术语高亮到位、块 ID 全局连续。**主要风险不在文字，而在视觉呈现方式**：46 块全部使用 `@visual: image`（AI 文生图），这是对成片质量影响最大的一个决定，下面按优先级展开。

---

## P0：影响成片可看性的问题

### 1. 全片 46 块均为静态文生图，无一块动画

每块旁白 6–9 行，按 TTS 折算单块约 25–40 秒。也就是说观众会**对着同一张静止图片看半分钟以上，全片十几分钟都是"幻灯片+淡入淡出"**，这是目前最伤观感的一点。

而且很多块的内容本质上是"过程"，静态图表达力天然不足：

| 块 | 内容 | 为什么适合动画 |
|----|------|--------------|
| B05 | 发布订阅 | 数据从 Publisher 流进 Topic 管道再流向 Subscriber，动起来一目了然 |
| B06 | 序列化 | 结构体逐字段"变成"字节流的过程 |
| B09 | RELIABLE vs BEST_EFFORT | 丢包→重传的回环动画 vs 丢了就丢，是天然的动效对比 |
| B11 | 延迟抖动 | 折线图逐帧绘制、峰值处闪红，比静态曲线有说服力得多 |
| B24 | 选型决策树 | 分支随旁白逐条点亮 |
| B08/B14 | 中心化→去中心化 | master 打叉倒下、网状连接逐条生成 |

**建议**：把上述 8–10 个"过程类"块改成 `@visual: animation`，并在 visual 描述里用 `[Xs]` 时间轴对齐旁白节拍（AUTHORING.md §3.1 支持）。animation 模式还有一个隐藏红利——文字由 React 渲染，**中文 100% 不会写错**（见下一条）。纯氛围块（B01 开场、B45 金句、B46 结尾）保留 image 没问题。

### 2. 文生图 + 密集中文标签 = 高翻车率

当前 visual prompt 普遍要求图里出现 **10–20 个精确中文/英文标签**（B23 层级图约 12 个带文字的方块，B24 决策树有 4 条分支 × 判断条件 × 推荐方案，B16/B32 是四行清单）。文生图模型对中文长文本的还原率很低，常见结果是错别字、乱码、标签张冠李戴。技术科普视频里图上文字写错，观众信任度直接归零。

**建议**：
- 凡是"文字就是内容本身"的块（清单、对比表、层级图、决策树：B10、B16、B23、B24、B27、B30、B32、B41、B42），改成 `animation` 模式让 React 渲染文字；文生图只负责"氛围/意象"类画面。
- 如坚持用 image，生成后必须逐张人工校对文字，并准备多次重roll的时间预算。

### 3. 图片底部文字会被字幕遮挡

渲染时字幕固定在画面底部（43px、宽 80%）。而两集几乎每一块的 prompt 都写了"**底部一行说明文字**"（B03、B07、B09、B11、B13、B22、B23、B24、B27、B31、B33…约 30 处），这行往往还是该图的点睛结论（如"实时 ≠ 快，而是可预测的最坏情况"）。成片后这些文字大概率被字幕压住。

**建议**：批量修改 prompt——把结论性文字移到画面**顶部或中上部**，并在所有 image prompt 末尾统一加一句"画面底部 15% 留空，不放任何文字"。animation 模式则可直接使用 `subtitleSafeBottom` prop 规避。

## P1：建议修改的问题

### 4. Prompt 中对文生图无效/有害的写法

- **占比与像素类指令**："整体占画面约 88%"、"字号 56px" 这类描述对文生图模型基本无效（AUTHORING.md §3.2 也明确图片模式不需要写字号布局），徒增 prompt 噪声。
- **负向指令**："不要画汽车"、"不要出现表格"、"不要只靠颜色区分"——多数 t2i 模型对否定句不敏感，甚至会因为出现该词反而画出来。建议改为正向描述（如"画面中只有分层矩形与文字"）。
- **Emoji 入图**：B28（⚠️）、B31（✈🚀🏥🏭）、B41（⚙️🌐🛡️🚗）要求模型画 emoji，产出风格不可控。建议改成描述性的图标语言（"一个简化的飞机线条图标"）。
- **十六进制色值**：`#0d1117`/`#58a6ff` 保留可以（部分模型能理解"深色背景、蓝色点缀"的意图），但不要指望精确到色号；46 张独立生成的图**风格漂移**是必然的，建议统一一段固定的风格前缀，减少每块自由发挥。

### 5. voiceRef 音频超出规范建议时长

`B00.wav` 实测 **48.4 秒**（44.1kHz / 16bit / 立体声），AUTHORING.md 建议 10–30 秒清晰人声。多数 TTS 音色克隆对超长参考音频要么截断要么效果劣化。**建议裁剪出最干净的 15–20 秒片段**替换（保留原文件亦可，另存一个 `B00-trim.wav` 指过去）。

### 6. TTS 发音风险词，建议提前试听

以下词在旁白中出现，TTS 读法不可控，建议构建后重点抽听、必要时改写拼读：

- `SOME/IP`（斜杠可能读成"some 斜杠 ip"）、`rmw_zenoh`（下划线）、`PREEMPT_RT`
- `ISO 26262` / `ISO 21434`（数字串读法）、`ASIL-D`、`gPTP`、`ros2 bag`
- `1.9 版`（B19，"一点九"应该没问题，但值得确认）
- `CyberRT`、`Zenoh`（专有名词发音）

### 7. 时效性信息被"烧进"画面

B19 的 visual prompt 要求图里写"截至 2026 年最新版为 1.9"，旁白也念了一遍。版本号写进图片意味着素材过几个月就作废。**建议图中删掉版本号只保留"活跃迭代中"，版本号留在旁白里**（旁白重录成本远低于重生成整块图）。

### 8. B43 新趋势块的事实核实

"CAPilot（学术论文，吞吐超 ROS2）"和"Hiroz（ZettaScale 的 Zenoh 原生 RMW）"属于冷门信息，视频一旦说错会被弹幕纠正。发布前建议再核实一遍两者的名称拼写与最新状态；旁白里已经加了"学术 benchmark 和工程实际有差距"的对冲，这个处理是好的。

## P2：锦上添花

### 9. 转场与节奏

46 块里 `fade-up`/`fade` 占绝大多数，`slide-left`（B23/B24/B31）和 `zoom-in`（B11/B28/B45）用在强调处，思路正确。可以再强化一点：**章节切换处**（如 ep1 进入 DDS 部分的 B12、ep2 进入量产部分的 B32）用区别度更高的转场或加一个 2–3 秒的章节隔断卡，帮观众建立"换章了"的感知。

### 10. 信息密度的呼吸感

ep2 的 B33–B39 连续七块都是"第 N 件事 + 卡片图"的同构节奏，中段容易疲劳。可考虑在 B36 或 B37 附近插一个轻量的"进度提示"（八件事已讲到第几件），或者把其中一两块合并压缩。

### 11. 结尾互动位置

B46 的"点赞/关注/留言"只出现在图片角落小标签里，旁白没有明确引导（只有"欢迎留言告诉我"）。数据上口播引导比画面标签有效得多，可在旁白里加半句。

- 两集切分点选得好：上集以决策树自收尾，下集用两个悬念问题承接
